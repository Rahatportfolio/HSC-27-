# Audit, roadmap and implementation report

## Before changes

On 2026-11-14 the checked-out repository at base `5008b0b31feb4ee82d7292768dcb9f78b1b12170` contained only the existing README. There was no application code, framework, package manifest, backend, API, authentication, database, storage integration or deployment configuration to audit or reuse. There was no existing app data or functioning UI to migrate or preserve. Accordingly this branch adds a new app rather than replacing an existing one.

## Roadmap and status

1. **Foundation:** mobile-oriented local-first shell and navigation, dashboard, editable subjects and user-entered/imported chapters implemented and exercised by automated tests. Device installation, real-browser offline behavior and a formal accessibility audit remain unverified; these are release verification gaps, not claims of completed device testing.
2. **Core and learning:** the local planner, timer, sessions, user-entered notes, practice, revisions, results and personal-question MCQ and self-marked written practice workflows are implemented and covered by automated tests. This is a baseline, not a complete official exam system; no official syllabus/question bank or automatic written-answer grading is supplied. Release/device verification is still outstanding.
3. **Advanced (in progress):** optional suggested planner tasks, same-exam/same-method score comparisons and recorded-session milestone/subject activity insights are available alongside the existing single-process backend for account sync, AI and background push. Important configuration and safety restrictions remain below; Bangla UI is partial. Sync has a narrowly scoped, explicitly confirmed additive merge, not general automatic merging.
4. **Quality/release:** automated Node/jsdom/mock tests and documentation exist, but production deployment, real Android installation, push delivery, provider access, full accessibility and formal security testing remain unverified. This is not a claim that every requested phase or item is finished.

## Architecture and data

The frontend is static HTML/CSS and vanilla JS (`js/app.js`, `js/views/`, `js/utils.js`, `js/store.js`), with no frontend build step. Browser `localStorage` key `hsc27_state_v1` holds schema version 1. `hsc27_sync_v1` holds per-device sync metadata. `hsc27_sync_base_v1` holds per-collection record IDs and SHA-256 hashes for the optional merge, not the complete snapshot or attachments; hashes are not encryption. The optional Node server uses `web-push`, writes version 1 JSON to `.data/study-data.json` (or `HSC_DATA_DIR`), and has one process-local in-memory database, a serialized atomic file-write queue, process-local sessions and rate limits. It is not a relational database and has no RLS. Server records have salted scrypt password hashes and per-user ID, revision, snapshot and push subscriptions. The HTTP handlers authorize access by session user; authenticated API endpoints other than session discovery also require an `X-HSC-User` ID matching that session, preventing stale clients from accessing a different account after a shared browser cookie changes. This ID is not a credential. Older cached/custom clients without this header must update. A full snapshot PUT is accepted only for the matching revision. No migration from an earlier app is needed (the base had no app); optional new fields preserve older local data. Existing unknown saved versions are not deliberately overwritten. There is no cloud schema migration framework.

State has `settings` (target, theme, intervals, exam date and notification preferences), optional `activeFocus`, `activeExam`, `activeQuiz`, `activeWritten`, `challenge`, and arrays `subjects`, `chapters`, `tasks`, `sessions`, `revisions`, `practice`, `exams`, `examResults`, `notes`, `formulas`, `resources`, `weaknesses`, `journal`, `weeklyReviews`, `milestones`, `questionBank`. References use subject/chapter/exam IDs where relevant. Calendar dates use `YYYY-MM-DD`, with Bangladesh time for current dates. Restore checks the version and top-level structure, not every field or relationship; import trusted backups only. Snapshots exclude active timers; general automatic per-record merging is not implemented.

13 subject names are seeded; chapter data is empty until entered/imported. Demo data is opt-in and not official syllabus data. Chapter percentages and priorities are personal judgments; no GPA guarantee is made.

## Feature summary and limitations

- Dashboard displays locally recorded time, tasks, exam date and completion. Lowest completion is **not** a measure of conceptual weakness.
- Subjects can be created and renamed; deletion is blocked while records are linked. Chapter names are unique within a subject for new entries. Chapters can be added, edited, reordered and imported from CSV/JSON. Imports accept up to 5,000 rows and 2,097,152 characters, skip malformed/duplicate rows and ambiguous subject names, and roll back on storage failure. Chapter deletion explicitly warns that linked tasks, revisions, practice, notes, formulas, videos and weaknesses are deleted; sessions, exams and questions are retained without the chapter link. Export a backup before deleting. Revisions are scheduled on completion using configurable day offsets. The planner shows day/week/month, carries unfinished tasks while the app is running or when opened, preserves the original date on carryover, supports task editing, manual rescheduling and optional task times, and saves preferred study hours (no automatic timed reminders). Rest tasks are excluded from planned study totals. Planned-versus-studied time is shown as a daily aggregate; sessions are not assigned to individual tasks. The optional planner preview proposes up to seven 30-minute tasks from upcoming/due revisions and active weaknesses and adds them only on confirmation. It fits existing planned (not actual) study minutes under the target over the next seven days, without checking real availability or assigning times. It deduplicates linked suggestions and pending correction tasks, not unrelated manual tasks; tasks do not complete their source revision or weakness. It is not a full automatic scheduling engine.
- Timer offers stopwatch, countdown and Pomodoro-style focus/break phases, plus manual study records. Timer state is saved locally and restored on reopening. An expired countdown records at most its target with an idempotent run ID, then enters a break on reopening; an expired break pauses before the next focus period. Stopwatch time continues while closed. If a session save fails, the elapsed time stays paused in memory for retry while the page remains open; a storage failure can prevent recovery after closing. Browser background alerts and long-break cycles are not guaranteed.
- Practice, mistakes, question bank, notes, formulas, videos, weaknesses, journal and exams are manually entered. Exam records can be associated with a chapter and format; a persistent countdown helps with a self-administered test using your own questions. Results are manually entered; illustrative grades and chapter averages do not independently assess components or guarantee official grading rules. A separate timed MCQ exam uses up to the first 50 matching four-choice questions from the user question bank, saves answers locally, scores with equal weighting and no negative marks, and offers answer review and mistake-to-weakness tracking. If closed, expiry is processed on reopening, not in the background. A separate timed written practice test takes up to the first 10 matching user-supplied CQ questions, persists typed answers, and on submission/expiry lets the student score each answer 0–100%. Its result uses equal question weights; answer/reference snapshots and self-marks are reviewable. It does not automatically grade answers or implement official board marking. Expiry is processed while open or when reopened. The separate manual timer does not administer answers or record marks. Full exam comparisons remain incomplete. Document links and local PDF attachments up to 512 KiB per note are supported. Attached PDFs are included in JSON backups/notes exports and are subject to limited browser storage; original files should be retained. Large PDFs and cloud file storage are not supported. No YouTube scraping or offline video downloading.
- The weekly review compares current retained task records with study time and can explicitly create 30-minute planner tasks from saved goals. It does not automatically create a personalized balanced plan, and edited/deleted task history is not a historical snapshot. Weakness records can create dated, repeated correction tasks in the planner. Analytics include valid linked chapter score averages and a same-exam, same-marking-method comparison of the latest two valid results (same-day results need distinct timestamps). Overall averages weight valid records equally and can mix marking methods; invalid/missing scores are excluded. These are descriptive, not predictions. A single personal challenge tracks actual daily time. A separate personal milestone history is calculated from valid, positive whole-minute retained sessions through today: 10/50/100/250/500 cumulative hours and first 3/7/14/30 consecutive study days. It also shows longest streak and subject activity for the last 14 days. The dates are recorded study dates, not award dates; edits or deletion change this derived history, and it is neither a certificate nor verified attainment. Opened resources record the last-opened timestamp. Broader analytics and certificates remain incomplete.
- Bangla input works throughout. A Bangla setting translates navigation, many form labels and controls, page headings and selected settings, but parts of the interface, messages and dynamic content remain English; user content is not translated. Dialogs now keep keyboard focus inside and restore it on close; selected icon-only planner controls have labels. Accessibility and low-end device performance have not been formally audited.
- In-app reminders run while open. Optional background web push uses the latest cloud snapshot and synced reminder settings; an active, configured server checks approximately once per minute and sends at most one aggregate reminder per device per Bangladesh day after the configured time. Browser permission, supported push services and network availability are required. Push delivery is not guaranteed or tested on real devices. Task-specific timed push and focus timer background delivery are not implemented.
- Optional AI requests go only through an authenticated, username-allowlisted server endpoint to OpenAI. The provider key stays server-side. Responses are labelled AI-generated and may be wrong; external provider usage can cost money. Real provider access has not been tested.
- Optional sync transfers full per-account snapshots, with revision checking and an offline dirty queue. Conflicts pause uploads and preserve both copies. After confirmation, a conservative merge supports only appended independent notes, sessions and journal entries if every pre-existing record, record order and settings match the secure baseline. It refuses deletions, edits, other record types, invalid links, missing IDs, duplicate IDs, missing/mismatched baseline or unavailable SHA-256. It saves the merged local copy and queues a revision-checked upload; it does not automatically resolve general conflicts. Users can download a plaintext cloud backup and export a local backup, then explicitly replace either local or cloud. Each replacement discards unique data in the replaced copy; cloud replacement is revision-checked, rejects concurrent remote writes, and queues newer local edits. Cloud pull aborts if local data changes during the request. Backups remain essential. Running focus, manual exam, MCQ and written tests remain device-local; finished result/review snapshots may be synchronized. Shared-device local data persists after logout. Backup files and server snapshots are unencrypted. Android installation, real offline behavior and lock-screen timing need device verification.

## Security and reliability

No provider or VAPID secrets are bundled. Production mode requires an exact HTTPS `PUBLIC_ORIGIN`, uses secure HttpOnly SameSite cookies, and binds to loopback by default for TLS reverse-proxy deployment. Mutations enforce same-origin checks, login uses scrypt and basic per-IP in-memory limits, request bodies are capped, static files are allowlisted, and the server serves a restrictive CSP. Push endpoints are restricted to supported services. These measures are not a formal audit: login throttling is per connection address (a reverse proxy may collapse clients to one IP), has no distributed coordination, and there is no hardened account recovery, session revocation/admin or encryption at rest. Multiple processes must not share the JSON file. Use a trusted host and TLS, protect the data volume and backups, and disable registration after creating accounts. Avoid simultaneous editing from multiple tabs sharing localStorage; the app is not a cross-tab collaborative editor. A shared origin, device access or malicious extensions can expose local data. The static-only deployment has no backend-supplied CSP.

Input validation, escaping and HTTP(S) URL checks are used, but import trusted files only. Local storage failures are surfaced; failed PDF writes and failed backup restores preserve previous data. Regular independent backups are essential. Sync uses full snapshots and may propagate reset or restore. The service worker caches the shell, not remote video or AI; HTTPS or localhost is required. No production URL is verified; GitHub Pages status lookup returned HTTP 403 due to integration permissions.

`npm ci && npm test` covers utility and store checks, foundation dashboard/navigation/subject/chapter/import/reorder, storage-failure and reload checks, Phase 2 planner edit/validation/carryover, session/timer failure retry, learning-link/transaction checks, question editing/pagination, written answer/self-marking/review/expiry and quota checks; Phase 3 opt-in suggestions, capacity, deduplication, quota rollback, score comparisons, derived milestone dates and subject activity, invalid-data exclusion and modal keyboard behavior; view renders, jsdom workflows (chapters, planner, focus recovery, exams, MCQ, PDF, imports, backup/quota failure, language selection), mocked service worker, real local HTTP backend auth/isolation/CSRF/revision conflict tests, multi-client sync/queue, cloud backup, explicit replacement, race handling, session expiry and cross-account isolation, limited additive merge, cloud-race retry and refusal cases, expanded Bangla labels and user-text preservation, review/journal/settings/challenge write-failure rollback, and mocked push scheduling and AI provider calls. These do not cover every form, timer path or security issue. The worker, AI provider and push service are mocked, not tested in real browsers or against external services. No actual Android, installed PWA, lock screen, real offline browser, production host, external AI or real push delivery test was performed.
