# Audit, roadmap and implementation report

## Before changes

On 2026-11-14 the checked-out repository at base `5008b0b31feb4ee82d7292768dcb9f78b1b12170` contained only the existing README. There was no application code, framework, package manifest, backend, API, authentication, database, storage integration or deployment configuration to audit or reuse. There was no existing app data or functioning UI to migrate or preserve. Accordingly this branch adds a new app rather than replacing an existing one.

## Roadmap and status

1. **Foundation and core:** mobile-oriented local-first shell, chapter management, planner, timer and sessions implemented, with the limits below.
2. **Learning:** user-entered notes, practice, results and a local MCQ exam are implemented in part; there is no supplied official syllabus or question bank and no automatic written-answer grading.
3. **Advanced:** basic analytics and an optional single-process backend for account sync, AI and background push are implemented, with important configuration and safety restrictions below. Bangla UI is partial.
4. **Quality/release:** automated Node/jsdom/mock tests and documentation exist, but production deployment, real Android installation, push delivery, provider access, full accessibility and formal security testing remain unverified. This is not a claim that every requested phase or item is finished.

## Architecture and data

The frontend is static HTML/CSS and vanilla JS (`js/app.js`, `js/views/`, `js/utils.js`, `js/store.js`), with no frontend build step. Browser `localStorage` key `hsc27_state_v1` holds schema version 1. `hsc27_sync_v1` holds per-device sync metadata. The optional Node server uses `web-push`, writes version 1 JSON to `.data/study-data.json` (or `HSC_DATA_DIR`), and has one process-local in-memory database, a serialized atomic file-write queue, process-local sessions and rate limits. It is not a relational database and has no RLS. Server records have salted scrypt password hashes and per-user ID, revision, snapshot and push subscriptions. The HTTP handlers authorize access by session user; a full snapshot PUT is accepted only for the matching revision. No migration from an earlier app is needed (the base had no app); optional new fields preserve older local data. Existing unknown saved versions are not deliberately overwritten. There is no cloud schema migration framework.

State has `settings` (target, theme, intervals, exam date and notification preferences), optional `activeFocus`, `activeExam`, `activeQuiz`, `challenge`, and arrays `subjects`, `chapters`, `tasks`, `sessions`, `revisions`, `practice`, `exams`, `examResults`, `notes`, `formulas`, `resources`, `weaknesses`, `journal`, `weeklyReviews`, `milestones`, `questionBank`. References use subject/chapter/exam IDs where relevant. Calendar dates use `YYYY-MM-DD`, with Bangladesh time for current dates. Restore checks the version and top-level structure, not every field or relationship; import trusted backups only. Snapshots exclude active timers; automatic per-record merging is not implemented.

13 subject names are seeded; chapter data is empty until entered/imported. Demo data is opt-in and not official syllabus data. Chapter percentages and priorities are personal judgments; no GPA guarantee is made.

## Feature summary and limitations

- Dashboard displays locally recorded time, tasks, exam date and completion. Lowest completion is **not** a measure of conceptual weakness.
- Chapters can be added, edited, reordered and imported. Revisions are scheduled on completion using configurable day offsets. The planner shows day/week/month, carries unfinished tasks while the app is running or when opened, preserves the original date on carryover, supports manual rescheduling and optional task times, and saves preferred study hours (no automatic timed reminders). Rest tasks are excluded from planned study totals. It is not a full automatic scheduling engine.
- Timer offers stopwatch, countdown and Pomodoro-style focus/break phases, plus manual study records. Timer state is saved locally and restored on reopening. An expired countdown records at most its target with an idempotent run ID, then enters a break on reopening; an expired break pauses before the next focus period. Stopwatch time continues while closed. Browser background alerts and long-break cycles are not guaranteed.
- Practice, mistakes, question bank, notes, formulas, videos, weaknesses, journal and exams are manually entered. Exam records can be associated with a chapter and format; a persistent countdown helps with a self-administered test using your own questions. Results are manually entered; illustrative grades and chapter averages do not independently assess components or guarantee official grading rules. A separate timed MCQ exam uses up to the first 50 matching four-choice questions from the user question bank, saves answers locally, scores with equal weighting and no negative marks, and offers answer review and mistake-to-weakness tracking. If closed, expiry is processed on reopening, not in the background. Written exams and the separate manual timer do not administer or automatically grade answers. Full exam comparisons remain incomplete. Document links and local PDF attachments up to 512 KiB per note are supported. Attached PDFs are included in JSON backups/notes exports and are subject to limited browser storage; original files should be retained. Large PDFs and cloud file storage are not supported. No YouTube scraping or offline video downloading.
- The weekly review compares current retained task records with study time and can explicitly create 30-minute planner tasks from saved goals. It does not automatically create a personalized balanced plan, and edited/deleted task history is not a historical snapshot. Weakness records can create dated, repeated correction tasks in the planner. Analytics include linked chapter score averages; a single personal challenge tracks actual daily time and displays completion/streak milestones. Opened resources record the last-opened timestamp. Advanced analytics, achievement history and certificates remain incomplete.
- Bangla input works throughout. A Bangla setting translates navigation, page headings and selected settings, but much of the interface remains English. Accessibility and low-end device performance have not been formally audited.
- In-app reminders run while open. Optional background web push uses the latest cloud snapshot and synced reminder settings; an active, configured server checks approximately once per minute and sends at most one aggregate reminder per device per Bangladesh day after the configured time. Browser permission, supported push services and network availability are required. Push delivery is not guaranteed or tested on real devices. Task-specific timed push and focus timer background delivery are not implemented.
- Optional AI requests go only through an authenticated, username-allowlisted server endpoint to OpenAI. The provider key stays server-side. Responses are labelled AI-generated and may be wrong; external provider usage can cost money. Real provider access has not been tested.
- Optional sync transfers full per-account snapshots, with revision checking and an offline dirty queue. Conflicts pause uploads and preserve both copies; there is no automatic merge. Cloud pull replaces local data after confirmation, so export a backup first. Running focus, exam and MCQ timers remain device-local. Shared-device local data persists after logout. Backup files and server snapshots are unencrypted. Android installation, real offline behavior and lock-screen timing need device verification.

## Security and reliability

No provider or VAPID secrets are bundled. Production mode requires an exact HTTPS `PUBLIC_ORIGIN`, uses secure HttpOnly SameSite cookies, and binds to loopback by default for TLS reverse-proxy deployment. Mutations enforce same-origin checks, login uses scrypt and basic per-IP in-memory limits, request bodies are capped, static files are allowlisted, and the server serves a restrictive CSP. Push endpoints are restricted to supported services. These measures are not a formal audit: login throttling is per connection address (a reverse proxy may collapse clients to one IP), has no distributed coordination, and there is no hardened account recovery, session revocation/admin or encryption at rest. Multiple processes must not share the JSON file. Use a trusted host and TLS, protect the data volume and backups, and disable registration after creating accounts. A shared origin, device access or malicious extensions can expose local data. The static-only deployment has no backend-supplied CSP.

Input validation, escaping and HTTP(S) URL checks are used, but import trusted files only. Local storage failures are surfaced; failed PDF writes and failed backup restores preserve previous data. Regular independent backups are essential. Sync uses full snapshots and may propagate reset or restore. The service worker caches the shell, not remote video or AI; HTTPS or localhost is required. No production URL is verified; GitHub Pages status lookup returned HTTP 403 due to integration permissions.

## Tests run

`npm ci && npm test` covers utility and store checks, view renders, jsdom workflows (chapters, planner, focus recovery, exams, MCQ, PDF, imports, backup/quota failure, language selection), mocked service worker, real local HTTP backend auth/isolation/CSRF/revision conflict tests, two-client sync/queue/account isolation, and mocked push scheduling and AI provider calls. These do not cover every form, timer path or security issue. The worker, AI provider and push service are mocked, not tested in real browsers or against external services. An attempted headless Chromium check could not start because the environment lacks `libnspr4.so`, `libnss3.so` and `libnssutil3.so`. No actual Android, installed PWA, lock screen, real offline browser, production host, external AI or real push delivery test was performed.
